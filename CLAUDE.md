# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Altunmak CRM" (`Altunmak CRM` / package name `makina-crm`) — a Windows desktop CRM for Altuntaş Makina, built with React (Vite) for the UI and Electron as the desktop shell. It tracks customers/machines, dealers, service requests, machine resale history, stock, spare parts, notes, and finance, and persists everything to a SQLite database (`data.db`) via `better-sqlite3` in `electron/db.cjs`. Supports a multi-user LAN mode: one PC acts as server (embedded Express + JWT, `electron/server.cjs`), others connect as HTTP clients; single-user local mode also works with no configuration.

## Commands

```bash
npm install          # install deps
npm run dev           # vite dev server + electron, hot reload (concurrently + wait-on)
npm run build         # vite build only (outputs to dist/)
npm run build:win     # vite build + electron-builder --win → release/*.exe (NSIS installer)
npm run preview       # vite preview of the built renderer (no electron shell)
npm run release       # build:win + electron-builder --publish always (pushes to GitHub Releases, needs GH_TOKEN env var)
```

`npm test` (vitest) runs the test suite: `tests/merge.test.js` covers the pure conflict-merge planner (`src/lib/merge.js`) under node; `tests/db-electron.test.js` spawns Electron to exercise the real SQLite layer (`scripts/tests/db-roundtrip.cjs` — migration, field roundtrip, table-skip integrity, audit retention), because better-sqlite3 is built against Electron's ABI and won't load under plain node. Pure helpers are covered by `tests/utils.test.js` / `tests/mail-templates.test.js` / `tests/permissions.test.js` / `tests/server-authz.test.js` (server-side write authorization, `electron/serverAuth.cjs`); component/regression tests live in `tests/ui/*.test.jsx` and run under jsdom via a `// @vitest-environment jsdom` pragma at the top of each file (plus explicit `afterEach(cleanup)` — auto-cleanup doesn't fire without vitest globals). `tests/server-security.test.js` spawns Electron to run the real embedded server end-to-end (`scripts/tests/server-security.cjs` — auth/401, per-user write authorization/403, admin-gating, password length, refresh-internal loopback, login rate-limit/429), same reason as the SQLite tests. **Rule: every bug fix ships with a test that would have caught it** (the UI tests exist because the permission-leak and "field not saved" bugs did). `npm run lint` (ESLint 9 flat config, `eslint.config.mjs`) targets real errors only — warnings are informational, keep the error count at zero. There is still no TypeScript. **CI (`.github/workflows/test.yml`)** runs lint + the non-Electron vitest suite on every push/PR (`hizli` job, Node 24) and the five Electron-spawning test files (`db-electron`, `server-security`, `image-optimize`, `security-flush`, `setup-admin-lockout`) under `xvfb-run` on main pushes/PRs/weekly (`electron` job: `npm ci --ignore-scripts`, then explicit `node node_modules/electron/install.js` + `electron-rebuild`, setuid `chrome-sandbox`). The split lives in `vite.config.js` (`VITEST_ELECTRON=skip|only`; unset = everything, as `npm test`), because vitest's `--exclude`/positional filters proved unreliable with several files. `release-integrity.yml` re-verifies every published release (three assets present, `latest.yml` sha512/size/url match the .exe). Other workflows: `audit` (npm audit), `gitleaks`, `typecheck`, `xlsx-version-check`; Dependabot version PRs (`.github/dependabot.yml`) + security-update PRs + CodeQL code scanning are on at the repo level.

To cut a new auto-update release: bump `"version"` in `package.json`, then run `set GH_TOKEN=ghp_...` (Windows) and `npm run release`. Auto-update (electron-updater) only works in the installed/packaged app, never in `npm run dev` or an unpacked build — `electron/main.cjs` explicitly checks `app.isPackaged` before touching the updater.

## Architecture

### Process split (Electron)
- `electron/main.cjs` — main process. Owns the data file at `app.getPath("userData")/data.json`, all `ipcMain.handle` channels (`crm:load/save/backup/restore/chooseFolder/writeBackup`, `updater:*`, `app:uninstall`, `app:printHtml`), window creation (splash + main window), single-instance lock, and security hardening (`contextIsolation: true`, `nodeIntegration: false`, blocks `will-navigate`/new windows to anything non-local).
- `electron/preload.cjs` — the only bridge between renderer and main, via `contextBridge.exposeInMainWorld`. Exposes three globals to the renderer: `window.crmStorage` (data persistence), `window.appPrint` (print-to-preview-window), `window.appUpdater` (update lifecycle events), `window.appControl` (uninstall).
- `src/main.jsx` — React root, mounts `<App />` wrapped in `<ErrorBoundary>`.
- `src/ErrorBoundary.jsx` — class component catching render errors app-wide; shows a Turkish fallback screen with a "Yeniden Başlat" button instead of a white screen.
- `src/App.jsx` — owns all top-level state and the sidebar/tab shell. There is intentionally no router; navigation is a `tab` state string with conditional rendering against a `TABS` array defined near the top of the file.

### Module layout (post-split)
The UI used to live entirely in one ~4700-line `App.jsx`. It's now split as follows — when adding code, put it in the matching module rather than back into `App.jsx`:
- `src/lib/constants.js` — pure data: embedded base64 logo reference, `ALTUNMAK_MODELS`, `COUNTRIES`/`COUNTRY_EN`/`COUNTRY_ALT`, `CITIES_TR`, seed arrays (`INIT_*`), `CURRENCIES`/`CUR_SYM`/`SALE_TYPES`/`DEFAULT_KDV_RATE`/`BACKUP_SCHEMA_VERSION`/`BACKUP_APP_TAG`/`SERVICE_TYPES`/`REPAIR_PLACES` (3 options: Yerinde Onarım, Fabrikada Onarım, Fabrika Teslim — "Kargo" was removed; `ServiceForm` still re-adds any legacy value not in the list so old "Kargo" records aren't silently changed on edit, and the `placeKargo` print translation is kept for printing them)/`APP_VERSION`.
- `src/lib/utils.js` — pure functions: date/currency formatting (`fmtTR`, `fmt`, `fmtCur`, `parseMoney`), Turkish-aware lowercasing (`trLower`), KDV/VAT math (`calcKDV`, `extractKDV`), a module-level mutable ID counter (`nextId`/`uid()`/`bumpId()`/`getIdCounter`/`setIdCounter` — not React state, used for generating new record IDs across the whole app).
- `src/components/ui.jsx` — UI primitives: `Icon`, `Field`, `Input`, `Warn`, `Select`, `MoneyInput`, `Btn`, `StatCard`, `Modal`, `ConfirmDialog`, `Pagination`, `CountryCityFields`, plus the `EMAIL_RE`/`PHONE_RE` regexes. All styling is inline `style={{...}}` objects — there is no CSS framework, CSS module, or styled-components.
- `src/hooks/useSimpleDefList.js` — shared hook factoring out the add/inline-edit/delete logic common to `KalipManager` and `PartManager` (both simple `{ad}`-only CRUD lists). `ModelsManager` is deliberately **not** built on this hook — it's modal-based, multi-field, and has separate std-vs-custom edit modes, so forcing it into the same shape would be an awkward abstraction.
- `src/hooks/useFilteredList.js` — shared hook factoring out the repeated "search + filter + paginate" pattern used by list screens (`Customers`, `SimpleDealers`, `Stock`). Takes the raw array plus `{ searchFields, searchFn, filterFn, sortFn, perPage }`; returns `{ search, setSearch, page, setPage, filtered, paged, perPage }`. `searchFields` covers plain own-field matching; `searchFn(item, query)` is for cases where the match target is reached via a join. `Customers` only takes the search+filter+page plumbing from the hook — its groupByFirm dedupe and multi-column sort run after the hook's `filtered`, since both need to operate in a specific order relative to each other that a generic `sortFn` param can't express. `Notes.jsx` keeps its own hand-rolled pager (different page size, no shared `Pagination` component) and wasn't migrated.
- `src/components/*.jsx` — one file per feature component, each a named export: `Dashboard`, `Customers` (shared by both the "Müşteriler" and "Bayiler" tabs via props like `isCustomer`/`entity`/`title`; its `detailView` modal is also where the former standalone "Makina Geçmişi", "Servis ve Yedek Parça", and "Extra Kalıp" tabs' functionality now lives — see below), `SimpleDealers`, `ServiceForm` (servis ekle/düzenle modal body, see below), `PartSaleForm` (Extra Kalıp satışı ekle/düzenle modal body, see below), `ModelsManager`/`KalipManager`/`PartManager` (used inside `Settings`), `Notes`, `Settings` (backup/restore, CSV/XLSX export, update UI, KDV rate, model/mold/part definitions), `Stock`, `Finance`, `Analiz` (see below).

A sale is bought **for a specific machine** OR **for the buyer's own reserve stock** (machine unknown), and the buyer later reports which machine(s) each part went on — so one 5-piece sale can be split across several machines over time. Derived status (code, not a column): 0 allocated → "Bayi stoğu (bekliyor)", `< miktar` → "Kısmi (n/miktar)", `= miktar` → "Tam bağlı". A batch shows as ONE card on the board and ONE event in the timeline (grouped by `batchId`; ops like drag/status/archive/delete/ödendi apply to the whole batch). **Sending to the Servis ve Kargo Panosu is now OPT-IN via a checkbox** ("📦 Servis ve Kargo Panosuna gönder", same pattern as Extra Kalıp/PartSaleForm) — `kargoDurum` defaults to `""` (NOT on board); checking the box sets `"Hazırlanıyor"`. Only the board's own "Yeni Yedek Parça Satışı" button pre-checks it (`kargoDurum:"Hazırlanıyor"`). Edit mode is single-line; editing a batch from the machine-history timeline opens the multi-line form and reconciles (delete old batch + recreate). Because the sale is now creatable from the customers/dealers/servis tabs (and deducts stock), `serverAuth.cjs` `BOLUM_SEKMELERI` for `yedekParcaSatislar`/`partStock`/`partStockLog` includes `"customers"`, `"dealers"`, `"servis"` (else those tabs' users 403 — guarded in `server-authz.test.js`). **Each of the four add entry points has its OWN permission id, in the dimension of the UserManager accordion it belongs to:** `yedek_parca_add` (stockActions, Stok tab), `cust_yedek_parca_add` (customerActions, customer detail), `dealer_yedek_parca_add` (dealerActions, dealer detail), `servis_yedek_parca_add` (customerActions in the "Makina Geçmişi — Servisler" group = the "Servis Panosu işlemleri" accordion, the board button). Normalized in `yedekParcaRec` (blanked when `teslimatFarkli` false, like `disFirma*`). A "Alıcının adresini doldur" shortcut copies the buyer's registered address into these fields as a starting point (source picked by `aliciTipi`: dealer record / customer record / `disFirma*`). ### Customers' detail view absorbed three former tabs: "Makina Geçmişi", "Servis ve Yedek Parça", "Extra Kalıp"
All three used to be separate top-level tabs. They were removed one at a time and merged into `Customers.jsx`'s `detailView` modal (opened by clicking a customer/machine row), on the reasoning that once every action is reachable from a customer's own profile, maintaining parallel "all customers" list tabs for the same data is redundant for this app's actual usage. **This was an explicit, deliberate product decision by the user** (not just a refactor convenience) — they were told the trade-off up front (losing cross-customer search like "all services by technician X", and losing a flat at-a-glance "who owes how much" list) and chose to proceed anyway, wanting to see how it feels in practice. If a future request asks to bring back a standalone list tab, that's not a contradiction of earlier work — it's revisiting a knowingly-provisional choice. Key points if touching this:
- `detailViewId` (not the record itself) is the state — `detailView` is derived live via `customers.find(c => c.id === detailViewId)` every render, so it reflects mutations (edits, 2nd-hand transfers, service/kalıp ödeme toggles) immediately instead of going stale like a stored snapshot would.
- The modal is two-column when the firm has more than one machine: a left "Bu Firmanın Makinaları" sidebar (click a row to switch which machine's detail is shown) and a right column with the field grid, "Sahiplik Geçmişi" (ownership chain, if resold), and the combined "Makina Geçmişi" timeline (sale + services + Extra Kalıp sales + warranty-end, built from `services` and `partSales`). With only one machine, the sidebar is hidden and the right column takes the full width.
- There is only ONE edit form for a customer/machine record — `openEdit`/`form`/`save` (the rich one with finance fields, `kaliplar` array, stock-linked serial selection). The old standalone `MachineHistory` tab had a second, simpler, partially-incompatible edit form (different field names: `kalip` singular vs `kaliplar` array, `note` vs `aciklama`) — that was deliberately dropped rather than carried over, to avoid two editors diverging on the same record. The same one-editor principle applies to services (`ServiceForm`) and Extra Kalıp sales (`PartSaleForm`): each has exactly one shared form, opened either fresh (pre-filled with `customerId: detailView.id`) or in edit mode from the timeline, never a second parallel form.
- "Yeni Sahip" (2nd-hand ownership transfer: `saveNewOwner`) and "Yazdır" (`printMachineReport`, the printable "Makina Servis ve Yedek Parça Geçmişi Raporu" for the whole machine) live in `Customers.jsx`, rebased onto `detailView`/`detailHistory`/`detailTimelineEvents`. There's also `printServiceForm(sv)` — the single-service "Servis Formu" printout (ported from the old `Services.jsx`, which had its own per-row Yazdır button); its button sits inline next to that service's title in the timeline, not in the modal's bottom action row, since it's per-record rather than per-machine.
- The "Satış Yapan" field (both in the main edit form and in the "Yeni Sahip" form's "Satan Firma" field) is a quick-pick `<Select>` (Fabrika / Bayiler / Önceki Sahip or Mevcut Sahip) layered over a free-text `<Input>` that holds the actual value — picking an option just fills the input, so any name (e.g. a previous owner who sold privately, not through the factory or a dealer) can also be typed directly.

### Data persistence pattern
- On mount, `App` calls `window.crmStorage.load()`. In local mode this reads from SQLite via `electron/db.cjs`; in client mode it fetches from the server via `electron/ipc/data.cjs`. If Electron APIs are absent (e.g. `npm run preview`), storage silently no-ops and data only lives in memory.
- Any change to the tracked state arrays triggers a `useRef`-backed 500ms debounced `window.crmStorage.save(...)` writing the entire state blob at once. **Saves are serialized through `src/lib/kayitSirasi.js` (`kayitSirasiOlustur`)**: the next save waits for the in-flight one and `__dataVersion` is stamped at send time from `dataVersionRef` (the body captured at state-change time carries a stale version). Without this, a second state change landing while a save was in flight (e.g. first-time auto-backup: folder pick save in flight → backup written → `lastBackup` set) went out with the old version and was rejected as a fake conflict ("Değişiklikler kaydedilemedi!" + needless merge). Real external changes still conflict. `flushSave` on unload also re-stamps the version. Guarded by `tests/kayit-sirasi.test.js` + `tests/ui/app-kayit-sirasi.test.jsx`. **The blob is the wire/IPC format only — SQLite does NOT store it as a blob.** `db.cjs` unpacks it into normalized, column-per-field tables (`customers`, `services`, `dealers`, …); the `meta` table holds only small key/value scalars (`dataVersion` etc.). Consequence: **adding a field to a record is not enough to persist it.** A new column must be added in four places or the value is silently dropped on the next load — `SCHEMA_SQL`, an `ensureColumns` entry in `applyColumnMigrations`, the `INSERT` column list + params, and the read/SELECT mapping. This has bitten before (`factory.ilce`); a roundtrip test in `scripts/tests/db-roundtrip.cjs` is the guard.
- SQLite writes are atomic via WAL mode; `electron/db.cjs` also keeps the old `data.json` atomic-write pattern (`fs.renameSync`) for the JSON fallback path.
- Schema migrations: `SCHEMA_SQL` holds the `CREATE TABLE` baseline, but newer columns are added incrementally via `ensureColumns` (idempotent). `migrateFromJsonIfNeeded` has three init branches — existing DB, clean install, and JSON→SQLite import — and **all three must call `applyColumnMigrations(conn)` after `SCHEMA_SQL`** (that function bundles every `ensureColumns` call). Regression to avoid: clean install used to run `SCHEMA_SQL` only, so a brand-new machine's first session was missing later columns (e.g. `uretim_formlari.baslangicTarihi`) and writing such a record crashed until the second launch. When you add a new column, add it to `applyColumnMigrations` (not just one branch); `scripts/tests/db-clean-install.cjs` guards the clean-install path.
- Multi-user mode: server PC runs `electron/server.cjs` (Express + JWT). Client PCs poll `/api/version` every 30 s and listen for `server:dataChanged` push events. Optimistic locking with `dataVersion` prevents silent overwrites (409 on conflict → reload). Entity-level pessimistic locking via `useLock` hook + `/api/lock` endpoint (2-min TTL, heartbeat every 60 s, fail-open). Records that are reachable from several screens share ONE lock area so they can't be edited from two places at once: a yedek parça (kargo) satışı locks `("yedek_parca", saleId)` from the Stok edit form, the **makinaya tahsis modal (`TahsisModal`)**, and the board's kargo detay modal; a service locks `("customer", customerId)` from both the customer detail and the board's service edit form; Extra Kalıp locks `("part_sale", saleId)`. **Servis ve Kargo Panosu box-drag** is an instantaneous action, so it does NOT hold a `useLock` (a held lock doesn't map to a drag); instead the board keeps a live lock list (`window.crmLocks.list()` refreshed on `server:locksChanged`) and, on drop, refuses the move + toasts if the dragged card's record is currently locked by **another** user (`baskasiKilitli` in `ServisPanosu.jsx`, keyed by the same three lock areas; own-user locks don't block). This is a soft guard on top of the optimistic `dataVersion` 409.
- Permissions are enforced on the server too, not just in the UI. The `makeCanDo`/`READONLY_SERVER_PERMISSIONS` model in `src/lib/permissions.js` hides buttons client-side; `POST /api/data` additionally re-checks it (`electron/serverAuth.cjs`): it diffs the incoming blob against the stored one section-by-section (`degisenBolumler`, key-order-stable) and rejects (403) any changed section the user's permission group blocks — so a crafted HTTP request from a read-only/restricted client can't overwrite data it can't edit in the UI. `BLOB_SECTIONS` lives in `serverAuth.cjs` (single source; `db.cjs` imports it) and every section must be mapped in `SECTION_GROUP` (a test enforces coverage). Limitation by design: the whole-blob save model can't distinguish add/edit/delete, so a group that is non-empty-but-partial (e.g. edit-but-not-delete) is trusted at the section level. **Two exceptions are enforced record-by-record in `eylemDenetimi`:** (1) ADD/DELETE — an unauthorized new/removed id is rejected via `EYLEM_IDLERI`; (2) **specific-field edits** — a curated `ALAN_IZINLERI` map re-checks a permission when ONE watched field changes, so **Kanban box-drag (status change) is server-enforced** for all three card types: `services.durum` requires `cust_service_edit`, `partSales.kargoDurum` (Extra Kalıp kargo card) requires `cust_kalip_edit`, `yedekParcaSatislar.kargoDurum` (yedek parça kargo card) requires `yedek_parca_edit`. Only that field is watched, so unrelated toggles (`ödendi`, `kargoSorumlusu`, `panoGizli`) stay section-level and don't false-positive. New records (id absent from the old blob) fall to the ADD branch, not the field branch. Guarded in `server-authz.test.js` + end-to-end in `server-security.cjs`. Full/admin users skip the diff (`kisitliMi` gate). This matters most once the server is reachable beyond the LAN (e.g. over a Tailscale VPN).
- **Rate limiting on the embedded server (three layers):** (1) a global `express-rate-limit` on every `/api` route (IP-based, 600 req/min, 429 with a Turkish `error` + `RateLimit` header; in-memory, resets on restart) — added mainly to cover CodeQL's `js/missing-rate-limiting` with a library it recognizes; `/health` and `/auth` are outside it; (2) the custom escalating brute-force lock on `/auth/login` (`rateLimit.cjs`, persisted in DB); (3) the per-user 60/min write limit on `POST /api/data`. The e2e script checks the global limiter LAST (601 requests → 429) because the window then blocks `/api` for a minute. **GitHub Code scanning (CodeQL default setup, JS + Actions)** is enabled on the repo; `pinnedFetch.cjs`'s `rejectUnauthorized:false` is a documented false positive (TOFU fingerprint fetch, dismissed on GitHub); workflows carry `permissions: contents: read`.
- Two server-authoritative logs, both admin-only, both pruned after 12 months: **security log** (`security_log`, "Kullanıcı Geçmişi", via `logSecurity` in `server.cjs`) and **audit log** (`audit_log`, "İşlem Geçmişi", via `db.writeAuditEntry`). Security log records auth/user-management events plus (added later): `sifre_degistirildi` (`PATCH /auth/me/password`), `cikis` (`POST /auth/logout`, called by the client's `server:logout` IPC before dropping the token), `oturum_yenilendi` (`GET /auth/me`, ~daily), `2fa_kurulum_baslatildi` (`POST /auth/2fa/setup`), `kilit_devralindi`/`kilit_birakildi` (force-steal / release on the lock endpoints). Server-PC-only local admin ops are logged straight to `security_log` from the IPC layer (not via HTTP) through `logYerelGuvenlik` (`ipc/data.cjs`) / `kaydetYerelGuvenlik` (`ipc/system.cjs`) — actor = config username, ip = `"yerel"`, no-op when the local DB is inactive (client PCs): `ilk_admin_olusturuldu`, `sunucu_baslatildi`/`sunucu_durduruldu`, `tls_modu_degistirildi`, `sertifika_yenilendi`, `sunucu_ayari_silindi`, `yedek_alindi`, `yedek_parolasi_degistirildi`, `uygulama_kilidi_kuruldu`/`_kaldirildi`/`_parolasi_degistirildi`.
- The audit log is otherwise **client-driven** — the client POSTs `/api/audit` with self-declared `action/entity` per user action (`src/lib/audit.js`, 61 call sites). To close the "crafted HTTP write leaves no trace" gap, `POST /api/data` now writes a server-authoritative **`veri_kaydedildi`** row for **every** write (admin included), entity `"sunucu"`, `entity_name` = changed section labels from `degisenBolumler` via `BOLUM_ADLARI`. This reads the stored blob on every write (the admin perf-skip of the authz diff no longer applies). File ops audit server-side too: `POST /api/files/upload` → `yuklendi`/`dosya`, `DELETE /api/files/:name` → `silindi`/`dosya`. Any new action/entity string must be added to the label maps in `SettingsSecurityLog.jsx`/`SettingsAuditLog.jsx` or it renders as its raw key; `SettingsSecurityLog` also surfaces the failed-login reason (`detail.sebep`) inline next to the `giris_basarisiz` label, and `SettingsAuditLog` now shows a Rol column. Covered end-to-end in `scripts/tests/server-security.cjs`. **Harness gotcha:** under Electron the check script's `process.exit(1)` is deferred (execution continues), so the failure path `return`s before printing the `TUM KONTROLLER GECTI` sentinel — the vitest wrapper asserts both exit 0 AND that sentinel, so a failed check can't slip through as a pass.
- Manual backup/restore and scheduled auto-backup go through separate IPC channels (`crm:backup`, `crm:restore`, `crm:chooseFolder`, `crm:writeBackup`) and write timestamped JSON files.
- New records get IDs from the global `uid()` counter, not from `crypto.randomUUID()` or DB-assigned IDs — when loading saved data, `bumpId(...)` scans existing records to advance the counter past any existing max ID.

### Faaliyet Haritası (the map tab)
- `src/components/Harita.jsx` + `src/components/harita/HaritaSvg.jsx` + `src/lib/mapStats.js`. Three drill levels: Dünya → ülke/il → ilçe. It's an "activity" map: every place that has sales is filled a **single logo orange** (`--hSatis`, not a density ramp) and gets a neutral location pin (`tur:"satis"`, theme-aware `--n900` so it stands out from the orange fill and the blue/green dealer pins) with the place name as a label; the factory and dealers/services are the other pins. **Every drawn place is name-labeled**, selling or not: selling ones via their satis pin, non-selling ones via a muted standalone label at the shape centroid (`yolMerkezi(d)` in `mapStats.js`). Labels live in the pin layer so they stay screen-px sized (readable when zoomed in, overlapping when zoomed out — accepted).
- **Map geometry is generated at build time, not fetched at runtime.** `scripts/gen-map-paths.cjs` turns upstream boundary data into plain JS modules under `src/lib/map/` (~8MB, **committed on purpose** — the app must work offline and the generator needs network + a local cache). Don't hand-edit anything in `src/lib/map/`; change the generator and re-run it. Companion: `scripts/gen-arkaplan-adlar.cjs` → `src/lib/map/world-arkaplan.js` (`ARKA_PLAN_AD` = Turkish names + projected centroids for the ~92 world countries **outside** the 86-country sales list, which `world.js`'s `ARKA_PLAN` stores nameless; territories below a projected-area threshold are skipped to avoid clutter, except a `KUCUK_ULKE` allowlist of small sovereign states (Luxembourg, Malta, Monaco, Andorra, Vatican, small island nations…) which are labeled regardless of size; dependent territories and geographic features stay excluded). It's **offline** — only `world-atlas` (local) + `d3-geo` (devDep) — and must reproduce `gen-map-paths.cjs`'s exact world projection + used-country set or the labels drift off the paths.

### Servis Panosu (the "servis" tab / service-floor kiosk)
- **Ayrı pencere (pop-out to a 2nd monitor), like Faaliyet Haritası but BIDIRECTIONAL.** The board can open in its own `BrowserWindow` (`servis.html` entry → `src/servis-main.jsx` → `src/components/ServisPencere.jsx`; `electron/preload-servis.cjs`; `electron/ipc/servis-pencere.cjs`; `main.cjs` `servisWin`; vite input `servis`). Unlike the read-only map window, this one is fully interactive, so the wrapper is a **two-way bridge**: (1) data flows down — `App` pushes a snapshot via `appServisPano.veriPush` (main-window preload) → `servis:veriPush` cached + forwarded → `ServisPencere` pulls (`servis:ilkVeriAl`) + lives (`servis:veri`), same race-safe pull+forward as the map; (2) writes flow up — every board setter (`setServices`/`setYedekParcaSatislar`/`setPartSales`/`setPartStock`/`setPartStockLog`/`setDosyalar`) is a shim in `ServisPencere` that applies the updater to its local mirror and sends the full resulting array as `servis:mutate {key,value}` → main process → `App.onMutate` applies `setX(value)`. **The main window stays the SOLE owner of state + persistence** (`App` is NOT mounted in the servis window — two savers would 409 each other, same reason `harita-main` avoids it). **Load-bearing subtlety:** the pushed snapshot sends the WRITABLE arrays in **FULL** (soft-deleted rows included) as the updater base, while `ServisPencere` renders `withoutDeleted(...)` for display — so a drag maps over the full array and the value returned to `setX` preserves soft-deleted records (dropping them would be silent data loss). The kiosk user's `stockActions` must stay unset/undefined (its default) — that's the group gate; UserManager only writes a `stockActions` array if the admin explicitly restricts it, so a plain `tabs:["servis"]` + `customerActions` user passes. `calisanlar` is a new BLOB_SECTIONS entry mapped to `settings` in SECTION_GROUP/BOLUM_SEKMELERI; and `servis` is in `serverPermissionDefs.js` `ALL_TABS` so UserManager shows the checkbox. Adding `durum` follows the usual four-place DB rule (SELECT auto for plain TEXT); `panoGizli` is INTEGER so its SELECT mapping is explicit (`toBool`).

Four-place DB rule (SELECT auto, plain TEXT); roundtrip-tested.
  - **İşçilik = mesai (working-hours) süresi, not wall-clock.** Labor (`isclikDk`) counts ONLY minutes falling inside the firm's working windows via `utils.mesaiDk(bas, bit, cs)` — nights, non-working days and breaks are excluded (else a Fri-evening→Mon service billed ~65h). **Bekleme and Toplam stay raw wall-clock** (real elapsed); only İşçilik is clamped, and `servisSureleri` also returns `isclikHamDk` (raw) for reference. ### Printing and export
- Printable documents (machine history report, service form) are built as raw HTML strings via template literals (not JSX) inside the relevant component, then sent through `window.appPrint.printHtml(html)`, which opens a visible Electron `BrowserWindow` preview with a Print/Close toolbar injected into the page (see `app:printHtml` handler in `main.cjs`). There's a browser-mode fallback (open as blob / download `.html`) when `window.appPrint` isn't available.
- **Print translations are per-document (`appSettings.translations`).** Teklif and Proforma are now edited independently (`SettingsTranslations.jsx` has NO shared "Ortak" section — the shared groups are re-emitted under each doc via `ortakGruplar(ns)`). Storage shape: `{ teklif:{TR,EN}, proforma:{TR,EN}, servis, makina, sandik, fatura }`. **The merge order in `buildPrintHtml` is load-bearing and must stay `DEFAULT < flat translations.TR/.EN (legacy shared pool) < translations[ns]` (`ceviriNs = isProforma ? "proforma" : "teklif"`)** — dropping the flat layer silently reverts existing users' customizations. `servis/makina/sandik/fatura` were already namespaced and are unaffected. `ceviri-kapsam.test.js` guards servis/makina key coverage; `print-templates.test.js` guards the teklif/proforma namespace + legacy fallback.
- **Proforma No (like the yurt dışı fatura's invoice no):** the proforma prints its `form.no` (year-based per-type sequence via `nextDocNo`, same as teklif) in the header badge AND the belge-info block (`L.proformaNoLabel` = "Proforma No"; EN proforma shows it in the FROM block). It's **editable in Evrak > Belge Detayları** (`Documents.jsx` `proforma_keys` includes `"no"`, label type-aware). **Adding a belge field is a two-place change:** the `*_keys` list in `Documents.jsx` AND `BUILTIN_BELGE.<type>` in `SettingsDocuments.jsx` (else the field renders but can't be hidden/reordered in Ayarlar > Evrak & Süreçler). `no` is NOT in `PROFORMA_SYNC_FIELDS`, so a proforma keeps its own number when its parent teklif is edited. Guarded in `print-templates.test.js` + `documents-defaults.test.js`.
- **Veri Yönetimi note:** JSON backup/restore (`SettingsBackup.jsx`) is whole-object, so new record fields ride along with no code change. The **CSV/XLSX export reports** (`SettingsExport.jsx`) are curated column lists, so a new field only appears if added there. The **Finans Özeti** export totals come from the pure `finansOzetiHesapla` (same file): service fee counts only for `isServisUcretliMi` services (Altuntaş, ücretli tip) and its KDV is added ON TOP via `calcKDV` (fees are entered KDV-hariç, Faturalı Yurtiçi only); Altuntaş parça (own service) and anlaşmalı parça (external-firm service, `altuntasParcaBedeli`) have their own lines + KDV, so the summary equals the report's BAKIM ONARIM section (`servisNet`/`servisBolumKdv`); rows come from the pure `finansOzetiSatirlari`. ### Conventions to preserve when editing
- All user-facing strings and form labels are in Turkish — keep new UI text consistent with this.
- Money fields are stored as raw numbers in state and only formatted for display (`fmtCur`/`fmt`); free-text money inputs go through `parseMoney()` to normalize Turkish thousands/decimal separators (`.`/`,`).
- `normalizeSaleType()` maps legacy sale-type strings to the current four-way `SALE_TYPES` (full Faturalı/Faturasız × Yurtiçi/Yurtdışı matrix: "Faturalı Yurtiçi" / "Faturalı Yurtdışı" / "Faturasız Yurtiçi" / "Faturasız Yurtdışı"). It recognizes already-current values as-is, then falls back to substring matching for legacy data — the old three-way system ("Faturalı Yurt İçi" / "Faturalı İhracat" / plain "Faturasız" with no yurtiçi/yurtdışı qualifier) and very old "Faturalı"/"Faturasız" data. Legacy "Faturasız" (no qualifier) defaults to "Faturasız Yurtiçi" since that data never tracked the distinction. Don't assume sale type fields are always already normalized when reading old/imported data — always run them through `normalizeSaleType()` first.
- When adding a new persisted state array in `App`, remember to (1) seed it in the initial load fallback, (2) include it in the debounced save effect's dependency array and payload, (3) include it in backup export/import and the XLSX template in `Settings` if it should be portable, and (4) **if it's an id-keyed record list, add it to `MERGE_KEYS` in `src/lib/merge.js` AND add an `apply(setX, "x")` line in `App.jsx`'s `mergeLocalIntoReloaded`.** Skipping (4) silently drops that array's just-added records whenever the conflict-merge runs — on a **single server PC** this fires from the app's own 5 s version poll (`calisanlar` disappeared "after a while" exactly this way). `mergeLocalIntoReloaded` only re-applies MERGE_KEYS *adds*; edits to pre-existing records still lose to the reloaded copy, so the save path also syncs `dataVersionRef` right after a successful `save()` to stop our own write from looking like an external change and triggering that reload. **`appSettings` is a singleton (not a MERGE_KEY list)**, and it had the same loss class: a reload's `setAppSettings(s => ({ ...s, ...disAppSettingsSuz(data.appSettings) }))` (App.jsx load) overwrote a local appSettings edit that hadn't round-tripped yet, so on **LAN/multi-PC** a just-toggled setting (e.g. the Analiz "Analiz'de Göster" checkbox = `analizGizliModeller`, or `musteriSutunlari`) reverted after close-open. Fix: `mergeLocalIntoReloaded` now also runs `setAppSettings(prev => mergeAppSettings(prev, myData.appSettings))` — `mergeAppSettings` (pure, in `utils.js`, tested) overlays this PC's local appSettings over the reloaded one (minus machine-local fields via `disAppSettingsSuz`), same "local change wins on merge" philosophy as MERGE_KEYS adds. Any new appSettings sub-field inherits this automatically (rides in the whole-object overlay); no per-field wiring.
